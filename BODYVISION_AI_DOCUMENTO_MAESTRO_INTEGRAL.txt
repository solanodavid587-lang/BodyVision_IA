1. VISIÓN, OBJETIVOS Y PRINCIPIOS DEL PRODUCTO 
1.1 Descripción 
BODYVISION AI es una plataforma web orientada a administrar expedientes, registrar mediciones corporales observadas, guiar capturas de 
imágenes, analizar landmarks de pose, visualizar activos 3D y comparar escenarios hipotéticos. La solución combina una experiencia 
Enterprise con una arquitectura modular y trazable. 
1.2 Objetivos del producto 
• Centralizar expedientes y datos de medición con historial y trazabilidad. 
• Guiar capturas con instrucciones y controles de calidad. 
• Procesar landmarks de pose mediante modelos de visión por computadora. 
• Visualizar activos 3D interactivos, con superficie, wireframe y capas de referencia. 
• Comparar mediciones registradas en distintos momentos. 
• Generar reportes que identifiquen origen, método, fecha y versión de los modelos. 
• Permitir escenarios hipotéticos sin modificar los datos observados. 
• Proteger la información mediante identidad, permisos, consentimiento y auditoría. 
1.3 Principios de integridad de datos 
Tipo de dato Definición Cómo debe presentarse 
Medición observada Dato ingresado manualmente o medido directamente con instrumento. Valor, unidad, fecha, método y responsable. 
Estimación visual Resultado inferido por un modelo a partir de una imagen. Etiqueta “Estimación visual”, calidad si existe y versión del modelo. 
Reconstrucción 3D Geometría aproximada generada desde datos disponibles. Etiqueta “Reconstrucción aproximada” y procedencia. 
Simulación Escenario hipotético con parámetros modificados. Etiqueta “Simulación”; nunca sobrescribe registros reales. 
Análisis temporal Comparación estadística de datos registrados en el tiempo. Periodo, datos incluidos, faltantes y método de cálculo. 
 
1.4 Límites del producto 
BODYVISION AI no debe presentarse como dispositivo médico, herramienta diagnóstica ni sistema de medición antropométrica clínica. La 
visualización 3D no constituye por sí sola un gemelo digital anatómico validado. Cualquier uso especializado debe someterse a evaluación 
técnica, legal y profesional.

3.2 Arquitectura de despliegue 
• El navegador entrega la aplicación frontend desde un servidor web o CDN. 
• El frontend consume exclusivamente la API autenticada. 
• FastAPI valida identidad, autorización, consentimiento y contratos. 
• PostgreSQL conserva entidades y referencias; los archivos binarios se guardan en almacenamiento de objetos. 
• Los medios se almacenan en object storage privado con claves no predecibles. 
• Los workers procesan imágenes y tareas de larga duración fuera del ciclo HTTP. 
• El visor 3D carga activos autorizados y optimizados; no accede directamente a la base de datos. 
3.3 Decisión Maya y 3D web 
Autodesk Maya se utiliza en la etapa de creación del activo: modelado, retopología, rigging, UV, materiales y exportación. El navegador no 
ejecuta Maya. El activo se exporta a GLB/GLTF, se optimiza y se visualiza con Three.js/React Three Fiber.

4.1 Convenciones de desarrollo 
• Una feature contiene componentes, hooks, validaciones y pruebas de su dominio. 
• Los componentes UI son reutilizables y no implementan reglas de negocio. 
• El cliente API centraliza base URL, tokens, errores, timeout y trazas. 
• Los schemas Pydantic validan contratos; los modelos ORM representan persistencia. 
• Los servicios contienen reglas de negocio; los repositorios encapsulan consultas. 
• Las migraciones Alembic son obligatorias para cambios de esquema. 
• Los secretos, archivos personales y modelos con licencia restringida nunca se suben al repositorio público.

5.4 Reglas de negocio 
• No procesar una imagen sin permiso sobre el expediente y consentimiento vigente para esa finalidad. 
• No mostrar ni exportar datos fuera del alcance autorizado. 
• No sustituir silenciosamente una medición previa: registrar corrección y motivo. 
• No mezclar una estimación visual con un dato manual como si fueran equivalentes. 
• No utilizar simulaciones para modificar la serie histórica de mediciones observadas. 
• Todo resultado de IA debe incluir versión de modelo, parámetros relevantes y estado de revisión. 
• Los archivos privados no deben servirse mediante rutas públicas permanentes. 
• El usuario debe distinguir entre dato observado, estimado, reconstruido o simulado.
